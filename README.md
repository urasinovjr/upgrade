# UpGrade

Сервис для репетиторов: загрузка решений учеников, разбор по шагам, проверка репетитором, публикация результатов и отчёты.

## Запуск всего стека

Нужен Docker. Из корня репозитория:

```sh
docker compose up -d --build --wait
```

| Адрес | Что открыто |
| --- | --- |
| http://127.0.0.1:8080 | приложение (nginx со сборкой `build:server` и прокси `/api`) |
| http://127.0.0.1:8025 | Mailpit: письма с подтверждением и сбросом пароля |
| http://127.0.0.1:8010/docs | схема API |

Остановить: `docker compose down`. Данные PostgreSQL и файлов сохраняются в томах `db_data` и `s3_data`; `docker compose down -v` удаляет и их. После изменения кода пересобрать: `docker compose up -d --build --wait`.

`GET /health` отвечает, пока процесс жив; `GET /health/ready` проверяет PostgreSQL и хранилище и отвечает 503 со списком `failed`, если что-то недоступно. `worker` раз в `HEARTBEAT_FILE_SECONDS` (10 с) обновляет файл `HEARTBEAT_FILE`, а аренду задачи продлевает раз в `HEARTBEAT_SECONDS` (1,5 с, всегда меньше `LEASE_SECONDS`), его healthcheck — `python -m app.heartbeat` (только стандартная библиотека, без импорта приложения). Образы backend и frontend работают без root: backend под пользователем 10001, nginx — непривилегированный на порту 8080 внутри контейнера.

## Выпуск

Production-стек описан в `compose.production.yaml`: PostgreSQL и SeaweedFS во внутренней сети без внешних портов, одноразовые миграции, API, два worker из общего образа и nginx с TLS. Приложение работает без root с файловой системой только для чтения. Образы задаются через `UPGRADE_BACKEND_IMAGE` и `UPGRADE_FRONTEND_IMAGE` по digest; `UPGRADE_RELEASE` содержит полный SHA и передаётся как `APP_COMMIT`. На сервере образы не собираются.

Постоянные каталоги на Ubuntu 26.04:

```sh
/opt/upgrade/config/production.env
/opt/upgrade/config/s3.json
/opt/upgrade/runtime/compose.production.yaml
/opt/upgrade/tls
/opt/upgrade/acme
/opt/upgrade/backups
/opt/upgrade/releases
/opt/upgrade/current
```

Шаблоны настроек находятся в `deployment/`. Секреты не хранятся в Git. Ключи S3 должны совпадать в обоих конфигурационных файлах. Снаружи доступны SSH, HTTP и HTTPS. Серверный приёмник из `backend/deployment/` устанавливается администратором в `/usr/local/lib/upgrade/deployment`, оболочки `upgrade-release`, `upgrade-ssh` и `upgrade-renew-tls` в `/usr/local/sbin`. Изменение серверного приёмника требует отдельной установки администратором.

Certbot 5.4.0 или новее выпускает IP-сертификат через webroot:

```sh
certbot certonly --preferred-profile shortlived --webroot \
  --webroot-path /opt/upgrade/acme --ip-address 193.233.218.52
```

Таймер `upgrade-certbot.timer` проверяет продление дважды в сутки. Hook копирует сертификат для nginx (uid 101), выполняет `nginx -t` и только затем reload. IP-сертификаты действуют около шести дней. nginx отдаёт HSTS и CSP; технические API закрыты, стенд отключён. `Production health` проверяет HTTPS, готовность БД и хранилища, здоровье контейнеров, остаток сертификата больше 24 часов, свободный диск и ежедневную копию не старше 30 часов.

Почта настраивается отдельным проектом UpGrade в Unisender Go. Отправитель: `UpGrade <upgrade@handmusic.space>`. В `UNISENDER_API_KEY` задаётся ключ проекта; домен отправителя должен быть подтверждён в его настройках. Настройки и ключ HandMusic сохраняются. Отслеживание прочтений и переходов отключено параметрами каждого письма.

### Проверка перед запуском и резервные копии

```sh
docker compose -p upgrade-production --env-file /opt/upgrade/current/release.env \
  -f /opt/upgrade/runtime/compose.production.yaml run --rm --no-deps api python -m app.cli preflight
sudo /usr/local/sbin/upgrade-release backup
```

`preflight` проверяет production-настройки, PostgreSQL, миграции, хранилище, конфигурацию ИИ и выбранный транспорт почты. Для Unisender выполняется `system/ping`, письмо не отправляется. Платных вызовов ИИ нет. Несовместимые настройки останавливают запуск API и worker.

Выпуск и ежедневная копия сериализуются блокировкой `/opt/upgrade/operation.lock`. Перед копией останавливаются API и worker, затем создаются `pg_dump`, архив файлов и манифест sha256. Хранятся семь ежедневных и две последние предрелизные копии. Таймер `upgrade-backup.timer` запускает ежедневную копию. После выпуска удаляются остановленные контейнеры только проекта UpGrade; остаются текущий и предыдущий наборы образов и файлов выпуска. Тома и общий Docker-кэш не очищаются. `upgrade-app.service` запускает активный выпуск после перезагрузки хоста: сначала БД и хранилище, затем сверяет ревизию схемы с образом и разрешает запуск API и worker. При несовпадении требуется ручное восстановление.

`python3 -m deployment.restore КАТАЛОГ -p upgrade-restore-check` из `backend` сверяет контрольные суммы, восстанавливает БД и файлы в отдельный проект с новыми томами и запускает `backup-verify`. Для установленного стека передайте `UPGRADE_COMPOSE_FILE=/opt/upgrade/runtime/compose.production.yaml` и `UPGRADE_RELEASE_ENV=/opt/upgrade/current/release.env`. Рабочая БД автоматически не восстанавливается. При отказе нового образа возвращаются предыдущие образы только при неизменной версии схемы. При изменении схемы API и worker остаются остановленными для ручного восстановления; downgrade не выполняется. Для ручного возврата совместимого выпуска извлеките поле `images` из его сохранённого `release.json` в отдельный JSON-файл. Передайте этот файл через `deployment.send_release --images`, указав прежний SHA в `RELEASE_SHA` и действующий токен чтения GHCR в `GH_TOKEN`. Приёмник сверит digest с сохранённой записью выпуска.

## Приёмка PRD

Тесты, которые закрывают функциональные проверки PRD, помечены номером сценария: `@pytest.mark.prd(n)` в backend и тегом `@prd-NN` в Playwright. Тест `tests/test_acceptance_matrix.py` проверяет, что у каждого из 16 сценариев есть тест, а сценарии интерфейса проверяются и в браузере. Сценарии 2 и 3 (альтернативное решение, верный ответ после неверного шага) в тестах проверяют подсчёт метрик; качество модели по ним измеряет срез `scenario` на наборе. Приёмочный набор запускается отдельно:

```sh
cd backend && uv run pytest -m prd
cd frontend && npm run e2e:prd
cd frontend && npm run e2e:docker:prd
```

## CI

`.github/workflows/ci.yml` запускается для каждого PR и коммита `main`, без фильтров каталогов. Обязательный итоговый статус `checks` требует успеха backend, frontend, browser, visual, security и production. Проверяются Ruff, pytest с PostgreSQL, обе code-shape, контракты, формат, ESLint, TypeScript, Vitest, три сборки, Chromium и WebKit, визуальные эталоны, зависимости, секреты и production-образы. Зависимости устанавливаются по lock-файлам, Actions и базовые образы закреплены. Автоматика использует только имитатор, ключи ИИ в ней пусты.

Production-образы конкретного SHA собираются один раз. После проверок TLS-стека, восстановления копии и повторных обновлений архив `checked-images` содержит их идентификаторы и sha256. После общего `checks` эти же образы загружаются из архива, проверяются и публикуются в GHCR. Сервер получает только SHA и digest через ограниченный SSH-доступ, без сборки. GitHub Environment `production` хранит `DEPLOY_KEY` и `DEPLOY_KNOWN_HOSTS`. Ключ имеет forced command и sudo только для `deploy` и `monitor`, не получает интерактивную оболочку или доступ к Docker.

## Визуальная регрессия на собранных экранах

Чтобы отделить снимки от пересборки dev-сервера, выполните:

```sh
cd frontend
VISUAL_STATIC=1 npm run e2e:visual:docker
```

Команда собирает две неизменяемые версии для демонстрационного и серверного
режимов, затем запускает тот же набор снимков, проверок доступности и размеров
320–1920 px. CI использует тот же режим сборки, чтобы dev-сервер и минификация CSS не меняли дробные размеры текста. Тестовые сборки сохраняют экран состояний; для выпуска используются
обычные `build` и `build:server`. Обновлять эталоны следует после просмотра
различий: `VISUAL_STATIC=1 npm run e2e:visual:docker:update`.

Серверные e2e можно направить на отдельный compose-проект через `E2E_BASE_URL`,
`E2E_MAILPIT_URL` и `E2E_COMPOSE_PROJECT`, чтобы не менять данные рабочего стека.
`E2E_WORKERS=1` запускает серверные браузерные сценарии последовательно, если локальные Docker-сервисы заняты другими проверками. В Linux CI `UPGRADE_BROWSER_CONTAINER=1` запускает серверные e2e в закреплённом Playwright-образе через сеть хоста; клиент Docker и Compose из runner подключаются для проверки тестовой БД. Браузеры и системные библиотеки повторно не скачиваются.

## ДЗ и ученический кабинет

Production включает маршруты ДЗ и ученического кабинета (`HOMEWORK_INTERNAL_TEST=true`),
без дополнительного пароля или ограничения регистрации. Текущий вариант:
`ANALYSIS_VARIANT=openrouter-qwen38-v1`. Результат проверяет репетитор перед
публикацией; экспертная оценка математического качества ведётся отдельно.
Прежние варианты и опубликованные промпты сохранены для истории.

Репетитор открывает «ДЗ», добавляет текст или фотографии условий, проверяет
обезличивание, распознаёт условия, сверяет и подтверждает задания. Сохранённый
черновик назначается нескольким ученикам. После назначения условия фиксируются;
срок можно изменить, исправления вносятся в копию. Из карточки ученика доступно
одноразовое приглашение. Перевыпуск отзывает прежний пароль и сессии.
Кабинет ученика: `/student`, вход: `/student/login`.

Навигация репетитора: «Обзор», «ДЗ», «Проверка», «Ученики». Условия вводятся
только в ДЗ, по этапам «Условия», «Сверка», «Назначение». Чтобы загрузить решение
за ученика, откройте назначенное ДЗ и нужного получателя. В «Проверке» находятся
сдачи: обезличивание фотографий, запуск разбора, сверка и публикация результата.
Старые работы сохраняются; `/works/new?student=…` перенаправляет к ДЗ с тем же
параметром ученика. API `/api/works` остаётся для совместимости.

Каждая сдача создаёт отдельную Work со снимком условий и привязкой файлов.
Пропуски и опоздания допускаются, новая попытка доступна после подтверждения
предыдущей. Фотографии незавершённой сдачи сохраняются в браузере. Черновики ИИ,
гипотезы и материалы отработки доступны только репетитору. Три упражнения с
ответами и решениями создаются по подтверждённому пробелу и редактируются вручную.
В демонстрации распознавание фотографий и материалы показываются на примерах.

Исходный текст сохраняется вместе с ДЗ; незавершённые правки восстанавливаются
на том же устройстве. Переход на другую страницу при несохранённых правках
требует решения пользователя. Для назначения нужно сохранить черновик,
подтвердить каждое условие и выбрать хотя бы одного получателя.

`GET /api/events` выдаёт события только своего кабинета: UTC, идентификатор,
версия схемы и приложения, источник `user`, `simulation` или `real`.
Событие записывается в транзакции изменения и не содержит условий, имён,
объяснений или изображений. Повтор сдачи с тем же ID не создаёт новую работу
или событие. Новая попытка сдачи получает новый ID; повтор обработки имеет ID
задания очереди. Пагинация: `limit`, затем `cursor=nextCursor`.
Подтверждение репетитором и публикация фиксируются отдельно, сейчас атомарно.
Журнал не восстанавливает события, случившиеся до его появления.

Для участников пилота `GET /api/timing/summary` разделяет активное время по
работе или ДЗ и этапам. Подготовка ДЗ и загрузка за ученика учитываются отдельно
от сверки разбора, отработки и экспорта. Ожидание ИИ хранится в заданиях очереди
и анализах и не прибавляется к активному времени. Техническая готовность ответа
не доказывает математическую корректность или экономию времени.

Версионированные контракты: `contracts/openapi-0.2.0.json` и
`contracts/postman-0.2.0.json`. Пересоздание: `cd backend && uv run python -m app.contracts`.
Postman содержит реальные маршруты и шаблоны тел; заполните переменные и
используйте отдельные сессии для двух ролей. Математические тесты с реальным
провайдером требуют настроенных `ANALYSIS_API_KEY` и `ANALYSIS_FOLDER_ID`.

API: `/api/homework`, `/api/homework/{id}/assign`, `/api/homework/{id}/recognize`,
`/api/homework-jobs/{id}`, `/api/students/{id}/invitation`,
`/api/assignments/{id}/submissions`, `/api/materials`; отдельный ученический API
находится под `/api/student`. Формат запросов описан в `/docs` сервера.
В версиях ФИПИ 2026 года: ОГЭ 25 позиций, базовый ЕГЭ 21, профильный 19;
проекты 2027 года: 25, 21 и 20 соответственно. Источники и хеши спецификаций
хранятся в `app/homework/exams.json`, тема знаний хранится отдельно от позиции.

Функциональные проверки расширения:

```sh
cd backend && uv run pytest tests/test_homework_api.py tests/test_homework_jobs.py tests/test_student_access.py tests/test_homework_gate.py
cd frontend && npm run e2e -- homework.spec.ts
cd frontend && npm run e2e:docker -- homework.spec.ts
```

Для выпуска нужны независимые экспертные наборы геометрии и остальных типов:
не менее 100 задач и 50 правильных решений в каждой группе. В геометрии нужны
планиметрия, стереометрия и доказательства. Пороги: ≥90% верных исходных разборов,
≤5% ложных ошибок на правильных решениях. Необоснованное уточнение считается
неверным разбором. После обычного `eval-run` и заполнения `expert.csv` выполните:

```sh
cd backend
uv run python -m app.evaluation.homework_gate --root /path/to/independent-set --run /path/to/run --materials /path/to/materials.csv
```

`materials.csv` содержит `material_id,exercise,reviewer,sha256,explanation_ok,condition_ok,answer_ok,solution_ok`:
по строке на каждое из трёх упражнений, эксперт указывает `yes` или `no`.
Неполный набор, отсутствующая разметка и непроверенные материалы блокируют приёмку.

## Frontend

React 19, TypeScript, Vite. Два режима одного приложения:

- демо (`npm run dev`, `npm run build:standalone`) хранит данные в IndexedDB браузера и не требует входа;
- серверный (`npm run dev:server`, `npm run build:server`) работает с API: регистрация, вход, подписка и данные на сервере. Режим включает переменная `VITE_API_URL` из `.env.server`.

```sh
cd frontend
npm install
npm run dev
```

Для разработки интерфейса с горячей перезагрузкой серверный режим можно запустить через Vite поверх стека из `docker compose`. Vite проксирует `/api` на `http://127.0.0.1:8010` (адрес меняет `API_PROXY_TARGET`):

```sh
npm run dev:server
```

Проверки:

```sh
npm run format:check
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium webkit
npm run e2e
npm run e2e:server
npm run e2e:docker
npm run e2e:visual:docker
```

`npm run e2e:server` и `npm run e2e:docker` проходят регистрацию, письмо в Mailpit, загрузку, разбор, подтверждение, режим только чтения и удаление на поднятом стеке. Отдельные сценарии проверяют работу с нечитаемой и неподдерживаемой задачей, отказ провайдера и ручной повтор, вторую редакцию и отзыв, недоступность чужих работ, учеников и файлов, совпадение скопированного текста и PDF одной редакции (PDF разбирается `pdfjs-dist`) и мобильный сценарий в WebKit (тег `@mobile`). Отказ задаётся маркером `[[fail:N]]` в условии: имитатор отвечает 503 на первые N распознаваний этой задачи. Перед регистрацией тесты очищают `rate_limits` через `docker compose exec`, чтобы не упираться в лимит входа. Первый сам запускает `dev:server` (порт 5173 должен быть свободен), второй проверяет контейнер `frontend` на порту 8080.

`npm run e2e:visual:docker` запускает визуальный набор в образе `mcr.microsoft.com/playwright:v1.63.0-noble`, том же, что и job `visual` в CI. Нужен только Docker; `node_modules` для Linux лежат в томе `upgrade-visual-node-modules`. Набор снимает экраны демо- и серверного режима (основное состояние на 390, 768 и 1440, остальные на 390 и 1440, включая пустые, ошибки и загрузку) и сравнивает их с эталонами в `e2e-visual/*-snapshots` без допуска по числу пикселей и цветовым отличиям. Ответы API подменяются в браузере, время, идентификаторы и анимации зафиксированы, перед снимком загружаются все шрифты. На каждом снимке проверяются горизонтальное переполнение, один `h1`, контраст текста, «сжатый» текст, ошибки в консоли и нарушения axe уровня serious и critical, включая поле формул MathLive и его shadow DOM. Отдельный свип (`sweep.spec.ts`) проходит каждый экран на 13 ширинах от 320 до 1920 в Chromium и WebKit и проверяет только вёрстку. После намеренного изменения интерфейса или обновления Playwright эталоны обновляет `npm run e2e:visual:docker:update`; если упал job в CI, отличия лежат в артефакте `visual-report`. `npm run e2e:visual` запускает тот же набор без Docker, но снимки на macOS не совпадают с эталонами, поэтому так полезно смотреть только проверки вёрстки: `npm run e2e:visual -- --ignore-snapshots`.

На ширине до 700 px клавиатура формул содержит разделы «Цифры», «Формулы» и «Буквы», страницы до 4×5 клавиш и цели от 44×44 px. Перед экспортом PDF все отображаемые формулы выбранной опубликованной версии проверяются MathLive; ошибка останавливает скачивание и указывает задачу и шаг. Сохранённые версии автоматически не меняются.

Переносимая сборка в один HTML-файл: `npm run build:standalone`.

## Backend

FastAPI, SQLAlchemy 2 (asyncpg), PostgreSQL, Alembic. Модульный монолит: пакеты `access`, `billing`, `students`, `knowledge`, `works`, `analysis`, `files`, `mail`, общая очередь `queue` и стенд `stand`.

Сервисы `compose.yaml` в корне репозитория:

Маршруты продукта находятся под `/api`, схема — на `/docs`. Изменяющие запросы с сессией передают заголовок `X-CSRF-Token` из ответа входа. Без активной подписки изменения отклоняются с кодом 402; просмотр, экспорт и удаление остаются доступны. Ошибки возвращаются как `{"detail": "<код>"}`.

### Разбор работы

Перед разбором каждая страница, которая уйдёт провайдеру, должна быть отмечена проверенной. `PUT /api/works/{id}/attachments` принимает у файла `masks` (до 20 прямоугольников на страницу в долях от размера страницы) и `checkedPages`. Отметка сохраняется, только если в этом же запросе не менялись кадр и маски страницы; поэтому маски и отметка отправляются разными запросами. Запрос, который меняет только отметки, не трогает ревизию черновика. Без отметок `analyse` отвечает 409 `redaction_unchecked` со списком `{fileId, page}`. Если имя или фамилия ученика из карточки встречается в условии, формуле, эталоне или шаге, `analyse` отвечает 409 `name_in_text` со списком `{taskId, field, stepId?}`. Проверка ищет слово с падежным окончанием без учёта регистра и «ё». Она учитывает уменьшительные формы из словаря частых имён (`app/analysis/name_forms.py`: Дарья — Даша, Дашенька, Дашуля; связь в обе стороны) и запись латиницей в нескольких вариантах транслитерации (Dasha, Daria, Ivanovoy). Другие формы имени репетитор указывает в карточке ученика: `PUT /api/students/{id}` принимает `aliases`, до 10 строк длиной от 1 до 40 символов. Они проверяются так же, как имя, и в отчёт не попадают. Имена короче трёх букв ищутся только кириллицей и целым словом, у трёхбуквенных форм на «а» и «я» учитываются падежи (Аня — Ани, Ане, Аню, Аней). Команды LaTeX пропускаются, а слова из стоп-списка (`max`, `sin`, «дано», «тем», «левая», «любой» и т. п.) не считаются именем, если только это не само имя или форма из карточки. Шаги, распознанные с изображения, перед вторым этапом проходят ту же проверку: найденное имя заменяется на «[скрыто]», в `analysis_runs.input.review` сохраняется отправленная копия. Если у задачи условие задано файлом, второй этап получает обезличенные страницы этого файла (те же байты, что ушли на распознавание); в `analysis_runs.input.reviewConditions` записываются задача, файл, страница, sha256 и размеры, без самих изображений. Условие можно задать и рамкой на загруженной странице (`conditionRegion`: файл, страница и область в долях оригинала). Рамка входит в подпись задачи, поэтому её изменение делает черновик устаревшим; при удалении файла она снимается. Для второго этапа область вырезается из обезличенной копии страницы, на распознавание передаётся её положение на копии. Промпт `math-1` изображения условий не использует.

Словарь форм и стоп-список frontend получает копией `frontend/src/data/nameForms.json`; после правки словаря её обновляет `uv run python -m app.cli names-json`. Тест следит, чтобы копия совпадала. Общие случаи проверки лежат в `frontend/src/domain/nameGuardCases.json`, их читают тесты backend и frontend.

Действие `POST /api/works/{id}/actions/analyse` ставит задачу `work_analysis` в очередь. `worker` читает файлы работы из S3 и вызывает адаптер провайдера в два этапа: `recognize` распознаёт шаги для задач без шагов (или для всех, если изменились файлы и порядок страниц), `review` выносит вердикты, тему и гипотезу о пробеле. Провайдер не получает исходные файлы. Перед распознаванием `worker` строит копию каждой страницы из `page_order`: PDF растрируется (pypdfium2, 150 dpi), фото поворачивается по EXIF, маски закрашиваются чёрным, затем применяется кадр и длинная сторона уменьшается до 2000 px. Изображение кодируется заново без EXIF, ICC и текстовых блоков: PDF и PNG в PNG, JPEG в JPEG. Копии лежат в хранилище под `teachers/{teacher}/works/{work}/sanitized/` и удаляются вместе с работой. Ключ, sha256 и размеры каждой копии записываются в `analysis_runs.sent_pages`. Провайдер получает эти страницы и условия задач без имени ученика, названия работы и имён файлов. Повреждённая или слишком большая страница завершает задачу кодом `page_unreadable` или `page_too_large` без повторов.

Распознанный шаг может указать номер присланной страницы и область на ней (`page`, `region` в долях копии). Сервер переводит область в координаты исходной страницы с учётом кадра и сохраняет у шага `origin {fileId, page, region, recognizedLatex}`. Если номер или область неверны, шаг остаётся без связи. Репетитор может только убрать связь: присланный клиентом `origin` заменяется сохранённым, у новых шагов его нет.

`GET /api/works/{id}/analysis/pages` перечисляет страницы текущего разбора, `GET /api/works/{id}/analysis/pages/{index}` отдаёт саму копию. В интерфейсе это раздел «Что получил ИИ».

Ответ проверяется на границе (`app/analysis/contract.py`): задачи и шаги только из запроса, темы только из справочника `app/knowledge`, у ошибки есть объяснение. Неверный ответ сохраняется с кодом `provider_invalid_response` и повторяется как сбой сети. Каждая попытка с ответом записывается в `analysis_runs`: входы, сырые ответы обоих этапов, черновик ИИ до правок, провайдер, модель, версия промпта, вариант разбора, коммит кода и длительности. API отдаёт черновик ИИ как `initialAnalysis`, происхождение — как `analysis` у работы и подтверждённой редакции.

Провайдер, модель, версия промпта и цены задаются вариантом разбора из реестра `app/analysis/variants.py`; `worker` берёт его из `ANALYSIS_VARIANT`, а `eval-run` — из `--variant`. Вариант `sim` использует адаптер имитатора (`provider-sim`, эндпоинты `/draft/recognize` и `/draft/review`). Вариант `yandex-qwen36-v1` обращается к Qwen3.6 35B в Yandex AI Studio через OpenAI-совместимый `/v1/chat/completions` (`app/analysis/openai_provider.py`): страницы идут в запросе как data URL, ответ ограничен JSON-схемой из версии промпта, заголовок `x-data-logging-enabled: false` отключает хранение запросов у провайдера. Вариант `yandex-qwen36-v2` использует ту же модель с промптом `math-2`: второй этап получает изображения условий (подпись «Условие задачи N»), справочник тем по семействам и справочник типов задач, возвращает `task_type_id`, а при типе вне охвата — `supported: false`; распознавание получает положение области условия и не переписывает её в шаги. В production выбран `openrouter-qwen38-v1`, описанный ниже; локальная разработка и CI используют `sim`. Тексты промптов и схемы ответа лежат в `app/analysis/prompts/`; опубликованная версия не меняется, правка оформляется новой версией (`tests/test_prompts.py` сверяет хеш). Модель возвращает прямоугольник шага в долях 0–1000 страницы, адаптер переводит его в `page` и `region`. Ответы 401/403 (`provider_auth`) и прочие 4xx (`provider_rejected`) завершают задачу без повторов. Ответ 429 (`provider_rate_limited`) откладывает задачу с растущей паузой и не расходует попытку; после `RATE_LIMIT_DEFERRALS` откладываний действует обычный повтор. Каждый процесс `worker` ведёт не больше `ANALYSIS_CONCURRENCY` разборов, письма и очистка файлов при этом продолжают обрабатываться. Два `worker` дают до двух одновременных заданий ИИ. Лимиты провайдера задаются выбранным вариантом и аккаунтом. Сценарий задачи выбирается детерминированно по её тексту: верное решение, ошибка с гипотезой, нечитаемый шаг или задача вне охвата (производная, вероятность, геометрия). Профиль `calm` отключает задержки и сбои.

### OpenRouter: Qwen3.8 27B

Вариант `openrouter-qwen38-v1` использует `qwen/qwen3.8-27b`, промпт `math-3`
и существующий HTTP-адаптер. Поддерживаются распознавание решений, математическая
проверка, распознавание условий и генерация трёх упражнений. Предыдущие варианты
и опубликованные промпты сохранены. Локальная конфигурация по умолчанию использует
`sim`; production использует `openrouter-qwen38-v1`.

Создайте отдельный ключ `upgrade-pilot` с лимитом **$1 без сброса**. В настройках
аккаунта отключите сохранение содержимого запросов, включите **ZDR only** и
исключите **Safety Retention**. Параметр запроса `zdr=true` сам по себе не исключает
Safety Retention. После проверки настроек укажите `OPENROUTER_PRIVACY_CONFIRMED=true`.
Подтверждение оператора обязательно; приложение не проверяет настройки аккаунта через API.
[Приватность OpenRouter](https://openrouter.ai/docs/guides/features/zdr).

Храните `OPENROUTER_API_KEY` в игнорируемом корневом `.env` с правами `0600`.
Шаблон переменных: `.env.example`. Не передавайте ключ через аргументы команд,
frontend, отчёты или логи. `ANALYSIS_API_KEY` и `ANALYSIS_FOLDER_ID` относятся к
Yandex; OpenRouter использует отдельный ключ и Bearer без заголовков Yandex.
Compose передаёт секрет только `api` и `worker`. Перед каждым платным вызовом
сервер читает `/api/v1/key`: отсутствие конечного лимита, лимит выше $1, сброс
лимита или неизвестный расход блокируют запрос. Лимит автоматически не изменяется.
[Проверка лимитов ключа](https://openrouter.ai/docs/api_reference/limits).

Маршрутизация фиксирована: `order=["nebius"]`, `allow_fallbacks=true`,
`require_parameters=true`, `data_collection="deny"`, `zdr=true`,
`max_price={"prompt":0.50,"completion":3}` в USD за миллион токенов.
Эти ограничения действуют и на резервные маршруты. Если подходящего маршрута
нет, возвращается `provider_route_unavailable`; ограничения не ослабляются.
[Параметры маршрутизации](https://openrouter.ai/docs/guides/routing/provider-selection).

Температура равна нулю. Распознавание использует 8192 выходных токена без reasoning;
проверка и материалы используют общий предел 16384 и reasoning-бюджет 4096.
`reasoning.exclude=true` исключает скрытые рассуждения из ответа. В JSON проверки
нет поля `reasoning`; старые схемы Yandex сохранены. Сервер отклоняет лишние или
пропущенные поля, обрыв по лимиту, неполный JSON и данные, нарушающие контракт.
Невалидный текст ответа OpenRouter не сохраняется. Идентификаторы задач и шагов
проверяются существующими прикладными правилами.

Общий предел `ANALYSIS_CONCURRENCY=1` охватывает разборы, распознавание условий
и отработку в каждом worker. При двух worker выполняется до двух заданий ИИ;
почта и очистка имеют свои слоты. Ответы 401/403, 402, ошибка настройки бюджета
и отсутствие маршрута завершают задание без повтора. 429 откладывает задание;
сетевые ошибки и 5xx используют ограниченные повторы общей очереди.

Миграция `0020` добавляет `analysis_runs.provider_calls` (JSONB) и nullable
`actual_cost_usd`. Каждый вызов содержит ID генерации, фактического провайдера,
возвращённую модель, токены, стоимость, длительность и параметры обработки.
`cost` сохраняет расчёт по настроенному верхнему тарифу, `actual_cost_usd`
содержит стоимость ответа OpenRouter. Если хотя бы у одного вызова стоимость
неизвестна, итоговая фактическая стоимость равна `null`; известные суммы остаются
в журнале вызовов. Происхождение Homework хранит аналогичный `providerCalls`,
включая неудачные попытки. Старые разборы получают пустой журнал и неизвестную
фактическую стоимость. Метаданные вызовов недоступны ученику; подтверждение
репетитором и проверка актуальности редакции сохранены.

В реестре также есть кандидат `openrouter-qwen38-v2` с промптом `math-4`.
Он сохраняет полноту распознавания и замечания по каждой задаче, различает
гипотезу пробела, отсутствие основания и недостаток данных. Один смысловой
повтор разрешён на весь разбор, только для проблемного этапа. Причина, оба
ответа и стоимость остаются в JSONB; состояние восстанавливается после
повтора worker. Повторный дефект оставляет доступный черновик «Нужна сверка».
Для той же версии входов новая платная цепочка не запускается: завершите
сверку вручную или исправьте входы. Новые маршруты и миграции не требуются.
Исторические ответы без признака полноты остаются с неизвестной полнотой.

Кандидат не включается автоматически. На синтетической регрессии он исправляет
отсутствующую гипотезу потерянного корня и подсчёт зависимых ошибок, но ещё
пропускает строки, ошибается в привязке страниц и формулировках обоснования.
Проверка этих правил: `uv run pytest tests/test_math4.py`. Метрики оценки
дополнены полнотой транскрипции, наличием и основанием пробела, зависимыми
ошибками; отдельные колонки `expert.csv` предназначены для экспертной сверки.
Синтетическая регрессия не заменяет приёмку реальных рукописей.

Отдельный технический пробник использует синтетические изображения без личных
данных и работает без БД приложения. Последовательно проверяет верное решение,
ошибку, геометрическое доказательство, нечитаемую страницу, отсутствие решения,
распознавание условия и три упражнения. Проверяет расход между вызовами,
останавливается при $0,80 или первом сбое, автоматических повторов не делает.
Синтетический набор не подтверждает качество распознавания реальных рукописей.

```sh
chmod 600 .env
cd backend
uv run --env-file ../.env python -m app.analysis.openrouter_probe --output ../output/openrouter-pilot.json
```

Отчёт содержит результат каждого случая, задержки, фактические маршруты, токены
и стоимость; ключ и скрытые рассуждения не записываются. Если статус `passed`,
установите в `.env` `ANALYSIS_VARIANT=openrouter-qwen38-v1` и сохраните
`HOMEWORK_INTERNAL_TEST=true`. Затем из корня проекта:

```sh
docker compose build api
docker compose up -d --no-deps --wait api worker
```

Приложение остаётся на `http://localhost:8080`, БД, подписки, S3 и остаток ключа
сохраняются. Для отката восстановите предыдущий `ANALYSIS_VARIANT` и пересоздайте
`api worker` той же командой. Новая миграция аддитивна и не требует отката схемы.
Публичный выпуск требует отдельной независимой математической приёмки.

Стоимость запуска считается по ценам варианта за миллион входных и выходных токенов, в рублях.

### Справочник тем и типов задач

Справочник хранится в коде: темы с предварительными знаниями — `app/knowledge/topics.py`, типы задач с отметкой охвата — `app/knowledge/task_types.py`, семейства — `app/knowledge/families.py`, версия и алиасы прежних id — `app/knowledge/catalog.py`. Темы из ответа ИИ и закрытия пробелов проверяются по справочнику; алиас заменяется действующим id. Frontend использует копию `frontend/src/data/catalog.json`, тест сверяет её с backend.

```sh
uv run python -m app.cli catalog-json
uv run python -m app.cli catalog-export --out ../output/catalog/algebra-1.xlsx
uv run python -m app.cli catalog-diff --xlsx ../output/catalog/algebra-1.xlsx
```

`catalog-json` обновляет копию для frontend. `catalog-export` пишет таблицу для эксперта: листы «Темы», «Связи» и «Типы задач» со столбцом «Замечание». `catalog-diff` показывает правки и замечания эксперта; их переносят в код и повышают `CATALOG_VERSION`. Если тема разделена, прежний id добавляется в `ALIASES`.

### Логи и отчёт о запусках

`api` и `worker` пишут в stdout по одной JSON-строке на событие: `ts`, `level`, `logger`, `event`, `request_id` и поля события. `LOG_FORMAT=text` включает читаемый формат, `LOG_LEVEL` задаёт уровень. Строка запроса содержит метод, шаблон маршрута, статус и длительность; адрес с параметрами, тела запросов и тексты учеников в лог не попадают. Заголовок `X-Request-ID` принимается от клиента (8–64 символа из букв, цифр и дефиса) или создаётся заново и возвращается в ответе. Для разбора он сохраняется в задаче и в `analysis_runs`, поэтому строки `api` и `worker` одного запуска связаны.

Каждый запуск хранит ожидание в очереди, время этапов, число токенов и стоимость. Сводку за период строит команда:

```sh
uv run python -m app.cli analysis-report --since 2026-10-01 --until 2026-10-31
uv run python -m app.cli analysis-report --csv > runs.csv
```

Сводка показывает число запусков и задач, коды ошибок, p50 и p95 по этапам и по ожиданию результата от постановки в очередь до готовности, а также стоимость всего периода, одной работы и одной задачи.

### Замер времени проверки

Замер нужен для главной метрики пилота: экономии активного времени проверки. Он включается только для участников пилота:

```sh
uv run python -m app.cli pilot-enroll --email teacher@example.com --note "пилот, группа 1"
uv run python -m app.cli pilot-enroll --email teacher@example.com --remove
```

`GET /api/timing` сообщает, включён ли замер. Остальные маршруты для других пользователей отвечают 403 `timing_disabled` и работают без подписки.

- `POST /api/timing/intervals` принимает до 200 интервалов активной работы `{id, workId, stage, startedAt, endedAt}`; `stage` — `preparation`, `masking`, `review` или `export`. Повторная отправка того же `id` ничего не добавляет. Интервалы длиннее 15 минут или из будущего отбрасываются (`rejected`). Интервалы неизвестных или чужих работ возвращаются в `unknownWorkIds`, и клиент может прислать их позже.
- `GET /api/timing/manual`, `PUT` и `DELETE /api/timing/manual/{id}` хранят замеры ручной проверки: ученик, число задач, семейство, измеренные и исправленные секунды.

Интерфейс в серверном режиме сам записывает активное время участника. Интервал идёт, пока вкладка видна и с последнего нажатия, касания или прокрутки прошло не больше двух минут. Он привязан к работе и этапу: новая работа (`preparation`), редактор масок (`masking`), проверка (`review`), отчёт (`export`). Интервалы длиннее 10 минут делятся на части. Очередь хранится в `localStorage` и отправляется раз в 30 секунд и при закрытии страницы (`keepalive`). Интервалы ещё не созданной работы ждут до суток. Участник видит в настройках, что замер идёт, но цифр не видит. Секундомер ручной проверки открывается на `/timing`.

Интервалы удаляются вместе с работой. Поэтому отчёт стоит выгружать до того, как участники удалят работы:

```sh
uv run python -m app.cli timing-report --since 2026-11-01 --until 2026-11-30
uv run python -m app.cli timing-report --csv > timing.csv
```

Отчёт учитывает только подтверждённые работы. Он показывает n, медиану, квартили и разброс активного времени для UpGrade и для ручной проверки, экономию `1 − медиана UpGrade / медиана ручной` (цель не меньше 0,50) в целом и на одну задачу, ожидание ИИ отдельно от активного времени, время по этапам и сводку по каждому репетитору. Если данных нет, он пишет «нет данных», а не ноль.

### Ручные исправления и гипотезы

Отчёт сравнивает ответ ИИ с первой подтверждённой версией каждой работы, у которой был автоматический разбор:

```sh
uv run python -m app.cli corrections-report --since 2026-11-01 --until 2026-11-30 --pilot
uv run python -m app.cli corrections-report --csv > corrections.csv
```

Текст шага сравнивается с распознанным текстом страницы, по тому же правилу, что и пометка «Не из оригинала». Без изменений; мелкая правка — изменилось не больше половины символов без учёта пробелов; переписан — больше половины; добавлен — у шага нет области оригинала; удалён — шаг ИИ не попал в версию. Вердикты, объяснения, тема, тип, пропуск задачи и гипотеза о пробеле сравниваются с запуском, на котором подтверждена версия. Исход гипотезы ИИ: принята, отклонена, удалена, без решения или тема изменена. Пробелы, которые репетитор добавил сам, считаются отдельно и в долю принятых не входят. Задача ИИ, которую репетитор удалил, считается вместе с её шагами и гипотезой. Работа, переведённая в ручной режим после разбора, остаётся в отчёте и считается отдельно. Правки следующих версий входят в строку «Исправлено после публикации».

Сводка идёт по всему набору, по варианту разбора (провайдер, модель, промпт), по семейству и по типу задачи. CSV содержит строку на задачу. `--pilot` оставляет только участников пилота, `--since` и `--until` фильтруют по дате первого подтверждения.

### Контрольный набор и метрики качества

Набор хранится отдельно от репозитория: каталог с обезличенными файлами и `manifest.json`.

```json
{
  "datasetVersion": "2026-11-01",
  "works": [
    {
      "workId": "w001",
      "split": "acceptance",
      "solutionGroup": "g001",
      "files": [{"path": "w001.jpg", "pageOrder": [1], "crops": {}, "masks": {}}],
      "tasks": [
        {
          "taskId": "t1",
          "family": "equations",
          "condition": "Решите уравнение …",
          "transcription": ["…", "…"],
          "correct": false,
          "firstErrorStep": 2,
          "explanation": "…",
          "topicId": "domain",
          "taskType": "rational_eq",
          "legibility": "legible",
          "admission": "admitted"
        }
      ]
    }
  ]
}
```

`split` — `dev` или `acceptance`. `solutionGroup` объединяет работы и повторные фото одного решения. Задача вне охвата получает `"admission": "excluded"` и `exclusionReason` ещё до прогона.

```sh
uv run python -m app.cli eval-validate --root ~/control-set --names names.txt
uv run python -m app.cli eval-run --root ~/control-set --split acceptance --out ~/runs/2026-11-01
uv run python -m app.cli eval-score --out ~/runs/2026-11-01
uv run python -m app.cli eval-run --root ~/control-set --split dev --variant sim --out ~/runs/sim
uv run python -m app.cli eval-run --root ~/control-set --split dev --variant yandex-qwen36-v1 --out ~/runs/qwen
uv run python -m app.cli eval-compare ~/runs/sim ~/runs/qwen --report ~/runs/compare
```

- `eval-validate` проверяет, что одна работа или группа решения не попала в обе части, в именах файлов и тексте карточек нет имён из `--names`, в файлах нет EXIF, текстовых блоков PNG и полей автора PDF, карточки заполнены (вывод, транскрипция, первый ошибочный шаг, объяснение, тема из справочника, причина исключения). Необязательные `conditionFiles` (номера файлов работы с 1) и `conditionRegion` (`file`, `page`, `region`) задают условие изображением. Поле `scenario` (`standard`, `alternative`, `right_after_wrong`, `unsupported`, `no_condition`, `illegible`) отмечает особые случаи PRD; `auto.json`, `eval-score` и `eval-compare` считают по ним отдельный срез. Необязательный `taskType` должен быть типом из справочника того же семейства; задачу с типом вне охвата нужно исключить с причиной. Также предупреждает, если в приёмочной части меньше 100 задач или 50 верных решений.
- `eval-run` прогоняет тот же конвейер, что и worker: копии страниц с масками и кадром, `recognize`, `review`. Вариант берётся из `--variant`, иначе из `ANALYSIS_VARIANT`; если контрольная часть прогнана не зафиксированным вариантом, команда предупреждает. Сохраняет `runs/<work>.json` (сырые ответы, время, токены, стоимость, вариант, коммит), `meta.json` (версия набора, вариант, коммит, модель, промпт, версия и хеш справочника тем, валюта) и `expert.csv` с автоматическим сравнением вывода, первой ошибки, темы и отказов. Без участия эксперта пишутся `tasks.json` (по задаче: совпадение вердикта и первой ошибки, ложная ошибка, отказ, тема, сходство распознанного LaTeX с экспертной транскрипцией) и `auto.json` (то же в целом, по семействам и по типам задач, с совпадением типа, плюс работы без ответа по причинам, p50 и p90 времени разбора, токены, стоимость). Сходство распознавания — `difflib.SequenceMatcher` по LaTeX без пробелов, `$`, `\left`/`\right` и отступов, шаги сопоставляются по порядку.
- `eval-compare` сводит `auto.json` нескольких прогонов в таблицу и пишет `compare.md`, `compare.csv` и `compare.json` в `--report`. Принимаются только прогоны части `dev`: контрольная часть служит для приёмки зафиксированного варианта, а не для выбора. Объяснения ошибок автоматически не оцениваются: их эксперт проверяет у отобранных вариантов через `expert.csv` и `eval-score`.
- Эксперт заполняет в `expert.csv` столбцы `explanation_ok` и `recognition_ok` (`yes`/`no`). `eval-score` без этих оценок не считает. Верный разбор: нет отказа, вывод совпадает, для ошибочного решения совпадает первый ошибочный шаг, объяснение и распознавание признаны верными. Порог — не меньше 90% верных разборов среди допущенных задач и не больше 5% ложных ошибок среди полностью правильных решений, в целом и по семействам. Результат дублируется в `metrics.json`.

### Стенд асинхронной обработки

- `POST /works` с заголовком `Idempotency-Key` сохраняет работу и задачу и сразу отвечает 202. `POST /sync/works` вызывает распознавание и разбор прямо в запросе.
- `worker` забирает задачи через `SELECT … FOR UPDATE SKIP LOCKED`, продлевает аренду и повторяет неудачные попытки с паузой. Продуктовые задачи используют ту же очередь.
- `provider-sim` имитирует OCR и LLM с задержками и сбоями по профилю `normal` или `degraded`.

- `POST /sync/works` с заголовком `Idempotency-Key` работает идемпотентно: работа с ключом сначала захватывается отдельной транзакцией, повтор с тем же ключом получает готовый результат (200) или 409 `work_in_progress`, пока идёт обработка; захват старше `SYNC_CLAIM_SECONDS` считается брошенным (например, API упал) и перехватывается повтором. При ошибке провайдера захват снимается.
- `POST /works/upload` и `POST /sync/works/upload` принимают те же данные формой (`meta`) со страницами и до обработки кладут страницы в S3 под `stand/<учитель>/<ключ>/<N>`.
- `PROVIDER_TIMEOUT` и `PROVIDER_CONCURRENCY` (0 — без ограничения, иначе число одновременных вызовов на процесс) передаются в `api` и `worker` из окружения compose, как и `RATE_LIMIT_DELAY` и `RATE_LIMIT_MAX_DELAY`. Ответ 429 откладывает задачу стенда, не расходуя попытку; нагрузочный клиент задаёт эти паузы в масштабе стенда (0,5 и 12 с). Прогоны стоит запускать на свободной машине: фоновая нагрузка хоста заметно увеличивает время готовности.

Нагрузочный прогон и сводка:

```sh
uv run python -m loadgen.run --mode sync-idem --level 1 --seed 1
uv run python -m loadgen.matrix --skip-done
uv run python -m loadgen.matrix --modes async --profiles normal --levels 5 --workers 2 --skip-done
uv run python -m loadgen.matrix --modes async --profiles normal --levels 10 --workers 5 --skip-done
uv run python -m loadgen.matrix --modes async --profiles degraded --condition t110-cap4 --skip-done
uv run python -m loadgen.matrix --levels 1 5 --profiles normal --condition storage --skip-done
uv run python -m loadgen.analyze
uv run python -m loadgen.analyze --protocol 1
```

По умолчанию `STAND_TIME_SCALE=0.1`: задержки имитатора и клиента сжаты в десять раз. Фактические затраты на БД, S3 и запуск процессов не сжимаются. Деление всего наблюдавшегося интервала на 0,1 даёт условный пересчёт, который требует отдельной проверки без сжатия.

Режимы: `sync`, `async`, `sync-idem`. Условия (`--condition`): `base`; `t110-cap4` — таймаут провайдера 110 с до сжатия и до четырёх одновременных вызовов на процесс; `storage` — страницы по 1,5 МБ передаются через S3. По умолчанию авария завершает API у синхронных режимов и worker у асинхронного. `--fault api` задаёт общий сценарий аварии API, `--no-crashes` отключает принудительные остановки.

Начиная с протокола 2 клиент опрашивает `GET /jobs/{id}`; готовность для клиента записывается в `polled_ready_s`, время записи в БД — отдельно в `ready_s`. Метаданные `restarts` содержат моменты остановки, запуска и готовности сервиса. Подвыборка `ready_p95_calm_real_s` относится к работам, чей интервал не пересёк перезапуск внутри прогона с авариями; она не заменяет отдельный опыт без аварии.

Анализ пересэмплирует целые прогоны: 2000 повторений с фиксированным seed 0. `lost` означает отсутствие работы и результата при итоговой сверке, включая отправки, не достигшие API. `acknowledged_missing` выделяет отсутствие записи после успешного ответа; `unconfirmed_missing` — без такого подтверждения. `ready_within_limit_share` считает результаты, увиденные за 120 с, от всех запланированных загрузок. Отсутствие результата остаётся в знаменателе. Число записанных результатов не измеряет число оплаченных вызовов провайдера.

Протокол 3 запускается с `STAND_PROTOCOL=3 STAND_TIME_SCALE=1`. Окно поступления составляет 600 с, таймаут клиента 30 с, пауза повторов 10 с, опрос каждые 2 с, аварии на 200-й и 400-й секундах. Ноль успешных ответов сохраняется как действительный исход; в старых протоколах действует прежнее правило `valid=false`. Результаты разных протоколов анализируются раздельно. `STAND_RESULTS_DIR` задаёт каталог протокола 3; `STAND_COMPOSE_PROJECT` и `STAND_COMPOSE_FILE` выбирают compose-проект и конфигурацию; `STAND_DATABASE_URL`, `STAND_API_URL`, `STAND_SIM_URL` и `S3_ENDPOINT_URL` — его адреса. Таймауты, аренду, продление и параллелизм сервисов нужно согласовать с масштабом времени в конфигурации compose.

Перед каждым прогоном `storage` пересоздаётся том `<STAND_COMPOSE_PROJECT>_s3_data`. Это удаляет объекты выбранного стенда: для исследования нужен отдельный compose-проект с отдельными портами и томами. Протокол 2 хранится в `backend/loadgen/results/protocol-2`, протокол 1 — в `backend/loadgen/results`. Запуск `loadgen.analyze` записывает `summary.csv` в каталог выбранного протокола; для повторного анализа исходного архива сначала следует сохранить прежнюю сводку.
